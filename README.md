# TickFlow

MVP таск-менеджера в духе TickTick. SwiftUI + SwiftData, минимальная версия iOS 26.

## Запуск

```bash
unzip ~/Downloads/TickFlow.zip -d ~/Desktop
open ~/Desktop/TickFlow/TickFlow.xcodeproj
```

Перед первым запуском поменяй `PRODUCT_BUNDLE_IDENTIFIER` (сейчас `com.ahito.TickFlow`)
и выбери свою команду подписи в Signing & Capabilities.

## Что уже есть

- **Списки** — цвет, SF Symbol, счётчик активных задач, каскадное удаление задач вместе со списком.
- **Смарт-подборки** — Сегодня (с просроченными), Ближайшие 7 дней, Все, Завершённые.
- **Задачи** — заметки, срок с началом и концом или без времени, приоритет, подзадачи, свайпы «Удалить» и «Сегодня».
- **Календарь** — режимы «Месяц» (сетка и повестка дня), «День», «3 дня» и «Неделя» (таймлайн по часам); нажатие на свободное время создаёт задачу, удержание блока и перемещение переносит её на другое время или день, а за нижний край — меняет длительность; задачу без времени можно перетащить из полосы «Весь день» на шкалу.
- **Поиск** — по названию, заметкам и названию списка.
- **Напоминания** — локальные уведомления для задач со временем, снимаются при выполнении и удалении.
- **Первый запуск** — три списка и демо-задачи через `SeedService`.

## Структура

```
TickFlow/
├── TickFlowApp.swift        ModelContainer и точка входа
├── RootView.swift           TabView: Задачи / Календарь / Поиск
├── App/                     AppDependencies: сборка зависимостей и создание view model
├── Models/                  TaskItem, TaskList, Subtask, Priority, TaskFilter, CalendarMode
├── Repositories/            Протоколы TaskRepository и TaskListRepository, реализация на SwiftData
├── Services/                NotificationScheduler, SeedService
├── DesignSystem/            Color(hex:), палитра, общие компоненты, форматирование дат
└── Features/                Home, Tasks, Lists, Calendar, Search: у каждого экрана View и ViewModel
```

## Архитектура

`View → ViewModel → Repository → SwiftData`

- **View** только показывает состояние и передаёт действия. Геометрия и жесты остаются в ней.
- **ViewModel** (`@Observable`) отвечает за состояние экрана, подборки, расчёт дат и правила.
- **Repository** — единственное место, где используются `ModelContext` и напоминания. View model зависят от протоколов.
- Данные обновляются сами: репозиторий перечитывает кэш после каждого изменения, а наблюдение обновляет экраны.
- View model получают модели `TaskItem` и `TaskList` напрямую, отдельного слоя DTO нет.

Проект использует синхронизированные группы Xcode (`PBXFileSystemSynchronizedRootGroup`):
новые файлы внутри папки `TickFlow/` попадают в таргет автоматически, редактировать
`project.pbxproj` не нужно.

## Осознанные упрощения

1. **Фильтрация в памяти.** Репозиторий держит все задачи в памяти, отбор идёт в вычисляемых свойствах view model.
   На сотнях задач это незаметно, на десятках тысяч — нет. Переход на `#Predicate` с
   `task.list?.id == id` стоит делать вместе с пагинацией.
2. **Нет повторяющихся задач.** Это отдельный RRULE-движок, а не поле в модели.
3. **Нет синхронизации.** Локальный store. Для CloudKit понадобится убрать уникальные
   ограничения и сделать все свойства опциональными или со значением по умолчанию —
   модели уже написаны с учётом этого.
4. **Ручная сортировка.** `sortOrder` есть в модели, но drag-and-drop в списке не подключён.
5. **Задача через полночь** на таймлайне обрезается концом дня и не переносится на следующий.
